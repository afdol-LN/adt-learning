PSU Adaptive Learning System (PSU ALS)

Version: 2.0 Status: Final Created: 2026-07-02 Updated: 2026-07-28

0. Document Purpose

This Product Requirements Document (PRD) defines the functional requirements, user journeys, success metrics, and MVP boundaries for the PSU Adaptive Learning System (PSU ALS). It is structured to provide PMs, UX designers, system architects, and developers with a clear and unified product blueprint. The document leverages a glossary-anchored vocabulary to avoid ambiguity. Key requirements are cataloged under globally stable IDs (FR-1.1 through FR-5.2), and specific design hypotheses are tagged in the body as [ASSUMPTION] blocks and aggregated in the index for verification.

ℹ Input references: This specifications sheet integrates and builds on the React + Vite frontend prototype located under go6-prototype and the TypeORM database schemas designed for NestJS.
⚠ Version 2.0 — what changed and why. The 2026-07-02 revision was marked Final and its quality review rated all seven dimensions "strong / Findings: None". A re-read against the actual schema and btk-engine found three defects that made the document unsafe to build from: (1) the P(L_0) formula could reach 0.99, above the 0.95 mastery threshold, auto-mastering a student before any exercise; (2) the prerequisite unlock rule contradicted itself across six files; (3) FR-5.1 mandated Case-Based Reasoning, for which no design, schema, or code existed. Six shipped modules also had no requirements at all, and §6.2 excluded an admin portal that was already in production. Decisions are recorded in docs/adr/0002-bkt-unlock-and-initial-mastery.md; that review has been re-run.
ℹ ID stability policy: FR-1.1–FR-5.2 and A-1–A-4 keep their original numbers so existing cross-references in the addendum, reconciliation note, and quality review stay valid. New requirements append as FR-6.x and above. This deviates from the flat-numbering convention in the PRD template, deliberately — renumbering would invalidate every existing reference at once.

1. Vision

Rigid, one-size-fits-all curricula in programming education struggle to engage diverse student bodies, leading to high dropout and failure rates. Advanced students are throttled by basic reviews, while beginners feel overwhelmed by sudden difficulty spikes.

The PSU Adaptive Learning System (PSU ALS) resolves this by establishing a dynamic learning loop that continuously matches curriculum pace and content to the individual learner. The platform discards superficial gaming overhead (such as character levels and fantasy RPG graphics) to focus student attention on conceptual progression.

Through an interactive, directed acyclic graph Concept Map (Skill Tree), students navigate connected skill nodes that unlock dynamically. Utilizing the Bayesian Knowledge Tracing (BKT) Mastery Engine to track student mastery probabilities, and selecting exercises whose difficulty matches that probability, PSU ALS ensures students receive micro-exercises calibrated to their zone of proximal development, reinforcing mastery without lecture bloat.

2. Target User

2.1 Jobs To Be Done

  • Self-Paced Progression: As a sophomore computer science/ICT student, I want to learn programming concepts at my own speed so that I do not feel left behind or bored.
  • Immediate Validation: As a student, I want to test my understanding of code blocks and get instant scoring feedback so that I can correct errors immediately.
  • Hands-on Assessment: As a user, I want to bypass video lectures and prove my competence directly through interactive code exercises.
  • Targeted Improvement: As a learner, I want the system to analyze my weaknesses and serve exercises that address those gaps directly.

2.2 Non-Users (v1)

  • Absolute Beginners: The platform is designed for students with basic introductory knowledge of variables and operations, serving as a supplementary adaptive coach.
  • External / non-PSU learners: Accounts are scoped to Prince of Songkla University campus, faculty, and major directories; there is no public self-service enrolment in v1.
ℹ Corrected in v2.0: this section previously listed "instructors seeking question authoring" as non-users, and §6.2 placed an instructor portal out of MVP scope. An Admin Portal covering user, skill, exercise, and history management is in fact built and shipping. Staff are now first-class users — see §4.7.

2.3 Key User Journeys

UJ-1: Afdol starts with a Pretest to skip variable basics.
Afdol, sophomore ICT student who already knows Python variables. • Authenticated, GetStart page.

Afdol starts his learning session and chooses the Pretest Gateway. The interface presents 5 diagnostic questions spanning variables, loops, functions, sorting, and graphs. He completes them, answering 3 correctly. The system scores his response times and correctness, setting his initial BKT mastery probability to Level 2 (Core) bounds. He lands on his Home dashboard, where the entire "Foundation" (T1) tier is marked as completed (progress 100%), and variables, operators, and basic I/O are unlocked. He goes directly to Loops to start exercises.

Edge Case: If Afdol leaves the app midway, his answers are cached, allowing him to resume or submit the pretest when he logs back in.

UJ-2: Student attempts a Locked concept node and is directed to prerequisites.
Student, wants to study OOP inheritance. • Dashboard, Interactive Concept Map.

The student views the dynamic Concept Map. Desiring to jump straight to OOP, they click on the locked OOP — Inheritance node. The Details Side Panel opens, displaying a locked state and listing Linked List (P(L_t) = 0.97, Mastered) and Recursion (P(L_t) = 0.62, not yet Mastered) under prerequisites. Because every parent must reach 0.95, the node stays locked on the strength of Recursion alone and the "Go to Exercise" button is disabled. Clicking the Recursion link highlights the connection line in the SVG map and slides the panel to that concept, where the button is enabled.

Edge Case: the panel shows Recursion at Progress 65% — a display value only. The student cannot unlock the child by reaching any partial percentage; only crossing 0.95 does it.

UJ-3: Ajarn Suda adds a new exercise to an existing skill before class.
Ajarn Suda, lecturer maintaining the React module. • Authenticated as Staff, Admin Portal.

Suda opens the Admin Portal and selects the Exercise tab. She searches the existing bank, sees 6 React items, and clicks "Add Exercise". She types the question, picks Level 2, selects the React skill from the active-skills dropdown, chooses CHOICE, and fills four options — ticking the checkbox beside the correct one. On save the item appears in the list as active and becomes immediately eligible for FR-5.1 selection. She spots a stale item, toggles its status to inactive, and it stops being served without the row being destroyed.

Edge Case: if she picks FILL_IN_BLANK the answer section swaps to a single expected-answer field plus a case-sensitivity checkbox, discarding the choice fields.

UJ-4: Afdol picks a career goal and gets a filtered skill path.
Afdol, the sophomore from UJ-1. • Authenticated, onboarding wizard after the pretest.

After the pretest, Afdol reaches the goal step and chooses "Backend Developer". The system creates a Branch linking him to that Goal and resolves the required skills from GoalskillRequire. His Concept Map now emphasises the skills that goal requires and shows a per-goal completion figure. He can hold more than one Branch — adding "Data Analyst" later gives him a second track without resetting mastery, because P(L_t) is per skill, not per goal.

3. Glossary

Concept Node (Skill) — A distinct learning unit in the tree (e.g., Loops) that contains a mastery probability P(L_t), progress status (0-100%), and dependency links.
Prerequisite — A directed edge on the map indicating that a parent Node must be Mastered (P(L_t) ≥ 0.95) before a child Node can unlock. See ADR 0002 §1.
Mastery Probability P(L_t) — A Bayesian probability (0.0 to 1.0) representing the likelihood that a student has mastered the concepts in a specific node. The only decision variable for unlock and completion state.
Progress — A display-only percentage derived from mastery, progress = min(100, round(P(L_t) / 0.95 × 100)). Rendered on the Concept Map as a completion bar. It never gates an unlock or a state transition. See ADR 0002 §2.
Concept Map (Skill Tree) — The visual DAG curriculum structure of concepts rendered in the UI with status-colored nodes.
Micro-Exercise — An interactive assessment item, supporting MCQs and fill-in-the-blank code snippets.
Session — A student attempt on a specific Concept Node node containing a block of 5 questions.
Behavior Profile — A categorization of learning behavior (Mastery, Fast, Steady, Slow, Struggler) based on time, accuracy, and momentum metrics. Display telemetry only; it never affects unlock or mastery state (FR-3.3).
Goal — A target career pathway (e.g. "Backend Developer") that maps to a required set of Skills at target levels via GoalskillRequire.
Branch — A student's active track toward one Goal. A student may hold several Branches; mastery is stored per Skill, not per Branch, so Branches share progress.
Staff — A user with the admin role who manages curriculum and accounts through the Admin Portal (§4.7). Distinct from Student, who consumes the learning loop.
Attempt — One recorded student answer to one Micro-Exercise, stored as a history row. At least one Attempt is required before a node may be marked Mastered (FR-3.2).

4. Features

4.1 Student Pre-test Gateway

Description: Assesses the user's initial proficiency to bypass redundant concepts. Realizes UJ-1.

FR-1.1: Pre-test Execution and Scoring

The system must serve a 5-question pretest covering tiers T1 to T3. Students cannot navigate back to edit submitted answers.

Consequences (Testable)
  • If a student clicks Next without picking an option, the system must trigger a warning modal.
  • The system must capture timestamps for each question submission to feed time profiling metrics.
FR-1.2: Initial BKT Probability Assignment

The system must calculate and assign initial concept mastery probabilities P(L_0) dynamically using a multi-factor formula that combines pre-test performance (accuracy and response time) and user profile inputs (selected learning goal, academic year, and user-inputted starting familiarity/experience level). The result is capped at 0.85 so that onboarding alone can never reach the 0.95 mastery threshold.

[ASSUMPTION: Dynamic BKT Onboarding Calibration] The initial mastery probability is calculated as P(L_0) = min(0.85, P_base(Familiarity) + ΔP(Pretest) + ΔP(Profile)), where Familiarity maps to Novice (0.15), Intermediate (0.45), and Advanced (0.75); ΔP(Pretest) awards up to +0.15 probability based on correctness and speed; and ΔP(Profile) awards up to +0.09 probability based on ICT/CS major correlation and Year 2+ enrollment. Without the cap the uncapped ceiling is 0.99, which exceeds the FR-3.2 mastery threshold and would auto-master every node before the student answers anything. See ADR 0002 §3.
Consequences (Testable)
  • An Advanced-familiarity, ICT-major, Year-2 student scoring 5/5 at maximum speed must receive P(L_0) = 0.85 exactly, and no Concept Node may be in the completed state immediately after onboarding.
  • Upon pretest completion, the system must update the profile's conceptMapState with the computed P(L_0) per node, and unlock a node only where every parent prerequisite satisfies the FR-2.1 unlock condition.

4.2 Interactive Concept Map (Skill Tree)

Description: Renders a visual mapping of the curriculum showing available and locked paths. Realizes UJ-2.

FR-2.1: Graph Rendering and Layout

The UI must render nodes with distinct styling corresponding to their states: Locked, Available, and Mastered. A node is Available when every parent prerequisite in skills_prerequisite has reached P(L_t) ≥ 0.95; it is Mastered when its own P(L_t) ≥ 0.95; otherwise it is Locked. Nodes with no prerequisites are Available from the start.

Consequences (Testable)
  • A locked node must show a locked lock icon, have greyed out text, and disable the Start button in its side panel.
  • A node with two parents at P(L_t) = 0.96 and P(L_t) = 0.94 must remain Locked — every parent must clear the threshold, not the average.
  • Displayed Progress must never affect node state: a node at Progress 94% (P(L_t) = 0.89) must still render as not-Mastered.
FR-2.2: Node Detail Side Panel

Clicking an unlocked or lockable node must slide in a details panel listing mastery probability P(L_t), derived Progress (display-only, per Glossary), prerequisites with each parent's current P(L_t), and descendant nodes.

Consequences (Testable)
  • For a Locked node, the panel must name which specific parent prerequisites have not yet reached 0.95, so the student knows where to go next.

4.3 Bayesian Knowledge Tracing (BKT) Mastery Engine

Description: Evaluates student mastery probability for each learning concept dynamically after every exercise response. Realizes UJ-1 and UJ-2.

FR-3.1: Latent State Estimation

The system must calculate the probability of mastery P(L_t) for each active Concept Node following the completion of any micro-exercise. The update calculation must use the KT-IDEM formulation — standard BKT Bayes update with guess and slip estimated per item rather than per skill (see Addendum §1.1).

[ASSUMPTION: BKT Node Mastery Threshold] A student is classified as having mastered a concept node when their calculated mastery probability P(L_t) meets or exceeds a 0.95 (95%) threshold.
[ASSUMPTION: BKT Parameter Seeding] KT-IDEM parameters are hand-seeded for v1, not fitted: P(G) = 1 / (number of choices) for CHOICE items and 0.05 for FILL_IN_BLANK; P(S) = 0.10 per item; P(T) = 0.10 per skill. These are refit from real attempt data after a pilot cohort — fitting before launch is circular, since the data only exists once students use the system. See ADR 0002 §5.
Consequences (Testable)
  • Two items tagged to the same Skill but with different P(G) must produce different posterior P(L_t) values for the same correct answer and the same prior.
FR-3.2: Concept Node Unlock Propagation

A Concept Node transitions to completed when both conditions hold: its mastery probability P(L_t) reaches or exceeds 0.95, and the student has at least one recorded attempt against that node. On transition the system sets the node's derived Progress to 100% and re-evaluates every descendant, unlocking those whose parents now all satisfy FR-2.1.

[ASSUMPTION: Mastery Requires Evidence] The attempt gate exists so a high onboarding P(L_0) can never by itself mark a node mastered. Combined with the 0.85 cap in FR-1.2 this is defence in depth — either guard alone closes the gap, but the pair also survives future re-tuning of the onboarding ceilings. See ADR 0002 §3.
Consequences (Testable)
  • A student who completes onboarding at the 0.85 cap must have zero nodes in completed state until they submit at least one exercise answer.
  • Unlock propagation must be transitive in a single pass: mastering a node whose child then satisfies all its parents must leave that child Available without requiring a page reload.
FR-3.3: Behavior Profile Classification

The system must classify each student into a Behavior Profile (Mastery, Fast, Steady, Slow, Struggler) from response time, accuracy, and momentum metrics, and persist it to userprofile.behaviorScore and userprofile.strengthWeaknessMatrix. The Behavior Profile is telemetry for display only — it must not influence node locks, unlocks, or mastery state, which remain driven solely by P(L_t) per FR-2.1 and FR-3.2.

Consequences (Testable)
  • Two students with identical P(L_t) values but different Behavior Profiles must see an identical set of unlocked nodes.

4.4 Interactive Micro-Exercises Loop

Description: Drives the low-latency game loop using Socket.IO gateways.

FR-4.1: WebSocket Gateways

Exercises must run over persistent WebSocket connections to support real-time question delivery and timers.

[ASSUMPTION: String Verification] MVP exercises validate code-blanks using string matching instead of executing arbitrary code on sandboxed containers.
FR-4.2: Real-time Evaluation

The latency budget is split by what each stage actually costs. Correctness feedback — validating the submitted answer in memory and emitting the result over the open socket — must complete within 50ms. End-to-end settlement — including the BKT engine call and durable persistence — must complete within 200ms at p95.

ℹ Why split: the original single 50ms budget covered validation, a cross-service call into the Python BKT engine, and a durable write. That is not achievable outside localhost. Splitting keeps the tight target where it drives perceived responsiveness and sets an honest bound on the rest. See ADR 0002 and SM-1.
Consequences (Testable)
  • The student must see correct/incorrect feedback without waiting on the BKT engine round-trip; the updated P(L_t) may arrive in a later socket event.
  • If the BKT engine is unreachable, answer validation must still succeed and the attempt must be queued for later mastery reconciliation rather than lost.

4.5 BKT-Based Adaptive Recommendation Engine

Description: Coordinates question selection and updates student mastery statistics at session finalization.

FR-5.1: Difficulty-Matched Pathing

The system must dynamically select the next micro-exercise whose difficulty best matches the student's current mastery probability P(L_t), using the per-item guess and slip parameters the KT-IDEM engine already stores (FR-3.1). Items whose predicted probability of a correct answer falls nearest a target band are preferred, so the student is neither given work they will almost certainly pass nor work they will almost certainly fail.

ℹ Scope change: this requirement previously mandated Case-Based Reasoning (CBR). No case representation, similarity metric, retention policy, or case-base table was ever specified, and none exists in the engine. CBR is deferred to v2 (§6.2); v1 uses the per-item difficulty signal that already motivated KT-IDEM over plain BKT. See ADR 0002 §4.
[ASSUMPTION: Cache Persistence] Active question responses and intermediate BKT state updates are written to Redis, with the finalized mastery probability P(L_t) and derived Progress flushed to PostgreSQL only when the session terminates.
Consequences (Testable)
  • For a student at P(L_t) = 0.30, the selector must not return the item with the highest predicted-correct probability among the candidate pool.
  • Selection must be deterministic given the same P(L_t), candidate pool, and item parameters, so a session can be replayed in tests.

4.7 Admin / Staff Portal

Description: A staff-facing dashboard for managing curriculum and accounts without direct database access. Realizes UJ-3. Built and shipping; documented here in v2.0 after previously being excluded from scope in error.

FR-6.1: Curriculum Management

Staff can create, view, update, and deactivate Skills, Skill Prerequisites, and Micro-Exercises (including choices and fill-in-blank answers) through the portal.

Consequences (Testable)
  • Deactivation is a status toggle, never a row delete — a deactivated Skill or Exercise must remain retrievable and re-activatable, and existing history rows referencing it must not break.
  • The Skill dropdown when authoring an Exercise must offer only active Skills.
  • A CHOICE exercise must not save unless exactly one choice is marked correct.
FR-6.2: Account Management

Staff can list Students, inspect an individual Student's campus, faculty, goals, session count, accuracy, and streak, and toggle a Student's account status between active and inactive.

Consequences (Testable)
  • Two Students sharing an identical full name must be independently selectable and independently toggleable — the portal must key on Student ID, never on display name.
  • Deactivating a Student must prevent login without destroying their mastery state.
FR-6.3: Cohort Reporting

Staff can view aggregate system state — total and active Students, total Sessions, mean accuracy, Skill count, most-attempted Skill, weekly session volume — and a searchable, grade-filterable attempt history across all Students.

Consequences (Testable)
  • Reporting is read-only: no portal report may mutate conceptMapState or any mastery value.

Feature-specific NFRs: every route under this feature must require the admin role (FR-7.3); a Student-role token must receive 403, not a filtered view.

4.8 Authentication & Accounts

Description: Registration, login, and role-based route gating. Underpins every other feature — previously assumed but never specified.

FR-7.1: Registration

A prospective Student can create an account supplying full name, birth date, gender, username, and password, then complete the onboarding wizard (§4.9) to attach campus, faculty, major, and Goal.

Consequences (Testable)
  • Usernames must be unique; a duplicate registration must fail with a field-level error rather than creating a second account.
  • Passwords must be stored hashed — a database dump must contain no plaintext password.
FR-7.2: Login and Session

A registered user can exchange credentials for a signed JWT, which the client attaches to subsequent API and WebSocket connections.

Consequences (Testable)
  • An expired or malformed token must yield 401 and redirect the client to the sign-in screen.
  • The WebSocket handshake (FR-4.1) must reject an unauthenticated connection rather than upgrading it.
FR-7.3: Role Gating

Every route is classified as public, student, or staff. Staff routes require the admin role; student routes require any authenticated user.

[ASSUMPTION: Middleware Currently Disabled] AuthMiddleWare and AdminMiddleWare exist in the codebase but are commented out in app.module.ts, so routes are presently unprotected. This FR specifies the intended target state; re-enabling the middleware is implementation work, not a new design.
Consequences (Testable)
  • A Student-role token calling any FR-6.x route must receive 403.
  • No route may read a user identity from a request body or query parameter — identity comes from the verified token only.

4.9 Goals, Branches & Onboarding

Description: Career-pathway selection and the wizard that collects the profile inputs FR-1.2 depends on. Realizes UJ-4.

FR-8.1: Onboarding Wizard

After registration a Student completes a stepped wizard capturing campus, faculty, major, academic year, and self-reported familiarity (Novice / Intermediate / Advanced), followed by the pretest (FR-1.1) and Goal selection (FR-8.2).

[ASSUMPTION: Missing Profile Columns] FR-1.2 consumes academic year and self-reported familiarity, but userprofile currently has columns for neither. Both must be added before FR-1.2 can be computed as specified.
Consequences (Testable)
  • The wizard must be resumable — abandoning it midway and returning must restore prior steps rather than restarting.
  • A Student cannot reach the Concept Map without a recorded familiarity value, since FR-1.2 would otherwise have no base term.
FR-8.2: Goal Selection and Branch Tracking

A Student can select one or more Goals. Each selection creates a Branch, and the system resolves that Goal's required Skills and target levels from GoalskillRequire to emphasise the relevant region of the Concept Map and report per-Goal completion.

Consequences (Testable)
  • Adding a second Goal must not reset or duplicate mastery: P(L_t) is stored per Skill, so a Skill shared by two Goals reports the same value in both.
  • Per-Goal completion must be derived from the Goal's required Skills only, ignoring mastery in unrelated Skills.

5. Non-Goals

  • RPG Aesthetics: No character levels, custom avatars, or game screens.
  • Media Management: Hosting or playing long-form video lectures.
  • Student Interaction: Chat, messaging, or forum features in v1.
  • Code Execution Sandbox: Running backend code blocks dynamically; validation is string-based in v1.
  • Case-Based Reasoning: Not in v1. Exercise selection is difficulty-matched against P(L_t) (FR-5.1). CBR requires a case representation, similarity metric, and case base that this product does not yet have and cannot populate without attempt history.
  • Public enrolment: Accounts are scoped to PSU directory data; no open sign-up or external identity providers in v1.

6. MVP Scope

6.1 In Scope

  • Registration, login, and role-gated routes (§4.8).
  • Onboarding wizard capturing academic year, familiarity, and Goal selection (§4.9).
  • 5-question Pre-test with capped initial mastery (§4.1).
  • Dynamic Concept Map (Python Data Structures) with grey/blue/green node states, unlock driven solely by P(L_t) ≥ 0.95.
  • Socket.IO-based exercise loop with real-time question timers.
  • KT-IDEM Mastery Engine with hand-seeded per-item parameters, plus Behavior Profile telemetry.
  • Difficulty-matched exercise selection (§4.5).
  • Admin Portal for curriculum, account, and cohort reporting (§4.7).
  • NestJS monolithic backend with PostgreSQL/TypeORM persistence and Redis caching.

6.2 Out of Scope for MVP

  • Adaptive SQL branch (deferred).
  • Case-Based Reasoning selection — deferred to v2. Needs a case base that only exists once v1 has collected attempt history; v1 ships difficulty-matched selection instead (FR-5.1).
  • Containerized Docker sandbox code execution.
  • Fitted BKT parameters — v1 hand-seeds them (A-5); refitting from pilot data is a v2 activity.
  • Machine learning SVD offline recalculations: Offline Collaborative Filtering updates are deferred to v2; v1 uses KT-IDEM plus difficulty matching.
ℹ Corrected in v2.0: "Instructor portal for question bank management" was previously listed here as out of scope. It is built and in production, and is now specified in §4.7.

7. Success Metrics

ID Metric Name Description / Target Validates
SM-1 Interaction Latency Answer-validation feedback under 50ms; full settlement under 200ms at p95, measured server-side from socket receipt to persistence acknowledgement. FR-4.2
SM-2 Time-to-Mastery 15% reduction in exercise attempts required to reach P(L_t) ≥ 0.95, versus a fixed-order control. Baseline: measured in the pilot cohort's first term by serving a control group exercises in fixed skill order; adaptive vs control compared on the same Skill set. FR-5.1
SM-3 System Engagement ≥ 25% of an enrolled cohort of 300 students active on any given weekday during term. FR-8.2
SM-4 Redis Cache Hit Concept map and profile query hit ratio over 90%. FR-2.1
SM-5 Curriculum Self-Service ≥ 90% of exercise and skill changes made through the Admin Portal rather than by direct SQL or migration, per term. FR-6.1
SM-C1 Completion Speed Counter-metric: Do not optimize speed if user accuracy falls below 65%. Counterbalances SM-2. FR-4.2
SM-C2 Premature Mastery Counter-metric: Do not optimize time-to-mastery if the share of nodes marked Mastered on fewer than 3 attempts rises above 10% — that signals the seeded P(G)/P(S) are too permissive, not that students learned faster. Counterbalances SM-2. FR-3.2, A-5

8. Open Questions

  1. How do we normalize whitespace and casing variations in fill-in-the-blank text inputs? (Proposed: backend text normalization removing double spaces and carriage returns before matching.) Still open — and note that history does not currently store the submitted answer, so a normalization bug would be undiagnosable in production (§11.2).
  2. Should BKT transition probability P(T) adjust dynamically based on student speed metrics? Closed: P(T) is fixed at 0.10 per skill for v1 (A-5). Dynamic adjustment is a v2 candidate once fitted parameters exist.
  3. PDPA: what consent text is shown at registration, how long are history rows retained, and what is the erasure procedure on request? Blocks any production cohort (§10.2).
  4. How are seeded P(G)/P(S) values reviewed once pilot data exists — who owns the refit, and on what cadence? SM-C2 detects a bad seed but does not assign the fix.
  5. The FR-3.2 evidence gate requires reading attempt counts. Should that count live in conceptMapState.attempts (fast, but duplicated state) or be derived from history (authoritative, but a query per check)?

9. Assumptions Index

A-1
Initial BKT probability P(L_0) is computed dynamically by combining self-reported familiarity base probability, pre-test correctness/speed metrics, and student profile variables (academic year & major), then capped at 0.85 so onboarding alone cannot reach the mastery threshold. (Section 4.1)
A-2
A student is classified as having mastered a concept node when their calculated mastery probability P(L_t) meets or exceeds a 0.95 (95%) threshold and at least one attempt has been recorded against that node. (Section 4.3)
A-3
Exercises use string-matching for fill-in-the-blank snippets instead of full sandboxed code execution in MVP. (Section 4.4)
A-4
Redis caches active session data and only flushes finalized BKT mastery probabilities to PostgreSQL when a session is finalized. (Section 4.5)
A-5
KT-IDEM parameters are hand-seeded for v1, not fitted from data: P(G) = 1/(choice count) for CHOICE and 0.05 for FILL_IN_BLANK; P(S) = 0.10 per item; P(T) = 0.10 per skill. Refit after a pilot cohort. (Section 4.3)
A-6
Displayed Progress is derived from mastery as min(100, round(P(L_t) / 0.95 × 100)) and is presentational only — it never gates an unlock or state transition. (Section 3, Section 4.2)
A-7
Staff manage curriculum and users through the Admin Portal (Section 4.7) rather than direct database access, and admin routes are gated by the same JWT layer as student routes. (Section 4.7, Section 4.8)
A-8
Auth and admin middleware exist in the codebase but are currently commented out in app.module.ts, leaving routes unprotected. FR-7.3 specifies the intended target state; re-enabling them is implementation work, not new design. (Section 4.8)
A-9
FR-1.2 consumes academic year and self-reported familiarity, but userprofile has columns for neither. Both must be added before the initial mastery formula can be computed as specified. (Section 4.9, Section 11.2)

10. Cross-Cutting NFRs

System-wide quality attributes not owned by a single feature. Feature-specific NFRs stay with their feature (e.g. admin role gating in §4.7).

10.1 Security

  • Passwords stored using a one-way hash; no plaintext or reversible encoding anywhere in the datastore or logs.
  • All API and WebSocket traffic over TLS in deployed environments.
  • User identity is derived from a verified JWT only, never from a client-supplied body or query field.
  • Fill-in-the-blank answers are compared as strings and never evaluated, executed, or interpolated into a query (see §5 Non-Goals).

10.2 Privacy (PDPA)

  • The system holds Thai personal data — name, birth date, gender, and institutional affiliation — and is therefore in PDPA scope.
  • Purpose limitation: profile fields are collected for mastery calibration (FR-1.2) and cohort reporting (FR-6.3) only.
  • Cohort reporting must be presented in aggregate; per-Student drill-down is restricted to the Staff role.
  • [NOTE FOR PM] Consent capture at registration, the retention period for history rows, and the erasure procedure are not yet decided. These are required before any production cohort — see §8 Open Questions.

10.3 Accessibility

  • Target WCAG 2.1 AA for student-facing screens.
  • Concept Node state must not be conveyed by colour alone — Locked / Available / Mastered each carry an icon or text label as well as a hue.
  • The exercise loop must be completable by keyboard alone, since it is the highest-frequency surface.

10.4 Compatibility and Scale

  • Current-generation evergreen desktop and tablet browsers. No IE support. Mobile-web is best-effort in v1.
  • Capacity target: 300 concurrent students in an exercise session, sized to a single large class cohort rather than campus-wide rollout.
  • Latency budget per FR-4.2: 50ms validation feedback, 200ms p95 end-to-end settlement.
  • Loss of the BKT engine or Redis must degrade the system to "answers still recorded, mastery reconciled later" — never to data loss (FR-4.2).

11. Data Model

Authoritative schema rationale lives in adt-learning/docs/database_architecture.md; this section records only what the PRD's requirements depend on. The relational schema is 15 tables, not the 13 described in earlier drafts — history and sessionAndExercise were omitted from that count.

11.1 conceptMapState contract

Per-student mastery is cached in Redis during a session and flushed as JSON into userprofile.conceptMapState (A-4), keyed by Concept Node ID:

{ "<skillId>": { "pL": 0.87, "progress": 92, "state": "unlocked", "attempts": 6 } }
  • pL — mastery probability P(L_t). The only decision variable.
  • progress — derived display value per A-6. Never read to make a decision.
  • state — locked | unlocked | completed, resolved per FR-2.1 and FR-3.2.
  • attempts — count backing the FR-3.2 evidence gate.
