PSU Adaptive Learning System (PSU ALS)

Status: Final Created: 2026-07-02 Updated: 2026-07-02

0. Document Purpose

This Product Requirements Document (PRD) defines the functional requirements, user journeys, success metrics, and MVP boundaries for the PSU Adaptive Learning System (PSU ALS). It is structured to provide PMs, UX designers, system architects, and developers with a clear and unified product blueprint. The document leverages a glossary-anchored vocabulary to avoid ambiguity. Key requirements are cataloged under globally stable IDs (FR-1.1 through FR-5.2), and specific design hypotheses are tagged in the body as [ASSUMPTION] blocks and aggregated in the index for verification.

ℹ Input references: This specifications sheet integrates and builds on the React + Vite frontend prototype located under go6-prototype and the TypeORM database schemas designed for NestJS.

1. Vision

Rigid, one-size-fits-all curricula in programming education struggle to engage diverse student bodies, leading to high dropout and failure rates. Advanced students are throttled by basic reviews, while beginners feel overwhelmed by sudden difficulty spikes.

The PSU Adaptive Learning System (PSU ALS) resolves this by establishing a dynamic learning loop that continuously matches curriculum pace and content to the individual learner. The platform discards superficial gaming overhead (such as character levels and fantasy RPG graphics) to focus student attention on conceptual progression.

Through an interactive, directed acyclic graph Concept Map (Skill Tree), students navigate connected skill nodes that unlock dynamically. Utilizing the Bayesian Knowledge Tracing (BKT) Mastery Engine to track student mastery probabilities, and incorporating Case-Based Reasoning (CBR) to select adaptive question pathways, PSU ALS ensures students receive micro-exercises calibrated to their zone of proximal development, reinforcing mastery without lecture bloat.

2. Target User

2.1 Jobs To Be Done

  • Self-Paced Progression: As a sophomore computer science/ICT student, I want to learn programming concepts at my own speed so that I do not feel left behind or bored.
  • Immediate Validation: As a student, I want to test my understanding of code blocks and get instant scoring feedback so that I can correct errors immediately.
  • Hands-on Assessment: As a user, I want to bypass video lectures and prove my competence directly through interactive code exercises.
  • Targeted Improvement: As a learner, I want the system to analyze my weaknesses and serve exercises that address those gaps directly.

2.2 Non-Users (v1)

  • Instructors seeking question authoring: The MVP is dedicated purely to student learning and session calculations. Editing concept nodes or question banks will be handled directly in the database.
  • Absolute Beginners: The platform is designed for students with basic introductory knowledge of variables and operations, serving as a supplementary adaptive coach.

2.3 Key User Journeys

UJ-1: Afdol starts with a Pretest to skip variable basics.
Afdol, sophomore ICT student who already knows Python variables. • Authenticated, GetStart page.

Afdol starts his learning session and chooses the Pretest Gateway. The interface presents 5 diagnostic questions spanning variables, loops, functions, sorting, and graphs. He completes them, answering 3 correctly. The system scores his response times and correctness, setting his initial BKT mastery probability to Level 2 (Core) bounds. He lands on his Home dashboard, where the entire "Foundation" (T1) tier is marked as completed (progress 100%), and variables, operators, and basic I/O are unlocked. He goes directly to Loops to start exercises.

Edge Case: If Afdol leaves the app midway, his answers are cached, allowing him to resume or submit the pretest when he logs back in.

UJ-2: Student attempts a Locked concept node and is directed to prerequisites.
Student, wants to study OOP inheritance. • Dashboard, Interactive Concept Map.

The student views the dynamic Concept Map. Desiring to jump straight to OOP, they click on the locked OOP — Inheritance node. The Details Side Panel opens, displaying a locked state and listing Linked List and Recursion under prerequisites. The "Go to Exercise" button is disabled. Clicking the prerequisite link highlights the connection line in the SVG map and slides the panel to that concept.

3. Glossary

Concept Node (Skill) — A distinct learning unit in the tree (e.g., Loops) that contains a mastery probability P(L_t), progress status (0-100%), and dependency links.
Prerequisite — A directed edge on the map indicating that a parent Node must reach at least 60% progress before a child Node can unlock.
Mastery Probability P(L_t) — A Bayesian probability (0.0 to 1.0) representing the likelihood that a student has mastered the concepts in a specific node.
Concept Map (Skill Tree) — The visual DAG curriculum structure of concepts rendered in the UI with status-colored nodes.
Micro-Exercise — An interactive assessment item, supporting MCQs and fill-in-the-blank code snippets.
Session — A student attempt on a specific Concept Node node containing a block of 5 questions.
Behavior Profile — A categorization of learning behavior (Mastery, Fast, Steady, Slow, Struggler) based on time, accuracy, and momentum metrics.

4. Features

4.1 Student Pre-test Gateway

Description: Assesses the user's initial proficiency to bypass redundant concepts. Realizes UJ-1.

FR-1.1: Pre-test Execution and Scoring

The system must serve a 5-question pretest covering tiers T1 to T3. Students cannot navigate back to edit submitted answers.

Consequences (Testable)
  • If a student clicks Next without picking an option, the system must trigger a warning modal.
  • The system must capture timestamps for each question submission to feed time profiling metrics.
FR-1.2: Initial BKT Probability Assignment

The system must calculate and assign initial concept mastery probabilities P(L_0) dynamically using a multi-factor formula that combines pre-test performance (accuracy and response time) and user profile inputs (selected learning goal, academic year, and user-inputted starting familiarity/experience level).

[ASSUMPTION: Dynamic BKT Onboarding Calibration] The initial mastery probability P(L_0) is calculated as P(L_0) = P_base(Familiarity) + ΔP(Pretest) + ΔP(Profile), where Familiarity maps to Novice (0.15), Intermediate (0.45), and Advanced (0.75); ΔP(Pretest) awards up to +0.15 probability based on correctness and speed; and ΔP(Profile) awards up to +0.09 probability based on ICT/CS major correlation and Year 2+ enrollment.
Consequences (Testable)
  • Upon pretest completion, the system must update the profile's conceptMapState, setting the progress of bypassed nodes corresponding to the calculated mastery bounds to 100% and unlocking their direct dependent nodes.

4.2 Interactive Concept Map (Skill Tree)

Description: Renders a visual mapping of the curriculum showing available and locked paths. Realizes UJ-2.

FR-2.1: Graph Rendering and Layout

The UI must render nodes with distinct styling corresponding to their states: Locked, Available, and Mastered.

Consequences (Testable)
  • A locked node must show a locked lock icon, have greyed out text, and disable the Start button in its side panel.
FR-2.2: Node Detail Side Panel

Clicking an unlocked or lockable node must slide in a details panel listing mastery probability P(L_t), current progress, prerequisites, and descendant nodes.

4.3 Bayesian Knowledge Tracing (BKT) Mastery Engine

Description: Evaluates student mastery probability for each learning concept dynamically after every exercise response. Realizes UJ-1 and UJ-2.

FR-3.1: Latent State Estimation

The system must calculate the probability of mastery P(L_t) for each active Concept Node following the completion of any micro-exercise. The update calculation must use the standard BKT Bayes formulation representing probability updates for both correct and incorrect outcomes.

[ASSUMPTION: BKT Node Mastery Threshold] A student is classified as having mastered a concept node when their calculated mastery probability P(L_t) meets or exceeds a 0.95 (95%) threshold.
FR-3.2: Concept Node Unlock Propagation

Once a student's concept mastery probability P(L_t) reaches or exceeds the 0.95 threshold, the system must set the node's progress to 100% and transition its state to 'completed', and subsequently update all descendant nodes to 'unlocked'.

4.4 Interactive Micro-Exercises Loop

Description: Drives the low-latency game loop using Socket.IO gateways.

FR-4.1: WebSocket Gateways

Exercises must run over persistent WebSocket connections to support real-time question delivery and timers.

[ASSUMPTION: String Verification] MVP exercises validate code-blanks using string matching instead of executing arbitrary code on sandboxed containers.
FR-4.2: Real-time Evaluation

User submissions must be validated, recorded, and returned within 50ms.

4.5 BKT-Based Adaptive Recommendation Engine

Description: Coordinates question selection and updates student mastery statistics at session finalization.

FR-5.1: Mastery-Based Pathing

The system must dynamically select the next micro-exercise using Case-Based Reasoning (CBR) to match the student's current mastery probability P(L_t) computed by the BKT engine.

[ASSUMPTION: Cache Persistence] Active question responses and intermediate BKT state updates are written to Redis, with the finalized mastery probability P(L_t) and completion progress flushed to PostgreSQL only when the session terminates.

5. Non-Goals

  • RPG Aesthetics: No character levels, custom avatars, or game screens.
  • Media Management: Hosting or playing long-form video lectures.
  • Student Interaction: Chat, messaging, or forum features in v1.
  • Code Execution Sandbox: Running backend code blocks dynamically; validation is string-based in v1.

6. MVP Scope

6.1 In Scope

  • 5-question Pre-test.
  • Dynamic Concept Map (Python Data Structures) with grey/blue/green node states.
  • Socket.IO-based exercise loop with real-time question timers.
  • Bayesian Knowledge Tracing (BKT) Mastery Engine to track probability of concept mastery.
  • NestJS monolithic backend with PostgreSQL/TypeORM persistence and Redis caching.

6.2 Out of Scope for MVP

  • Adaptive SQL branch (deferred).
  • Instructor portal for question bank management.
  • Containerized Docker sandbox code execution.
  • Machine learning SVD offline recalculations: Offline Collaborative Filtering updates are deferred to v2; v1 uses BKT + CBR.

9. Assumptions Index

A-1
Initial BKT probability P(L_0) is computed dynamically by combining self-reported familiarity base probability, pre-test correctness/speed metrics, and student profile variables (academic year & major). (Section 4.1)
A-2
A student is classified as having mastered a concept node when their calculated mastery probability P(L_t) meets or exceeds a 0.95 (95%) threshold. (Section 4.3)
A-3
Exercises use string-matching for fill-in-the-blank snippets instead of full sandboxed code execution in MVP. (Section 4.4)
A-4
Redis caches active session data and only flushes finalized BKT mastery probabilities to PostgreSQL when a session is finalized. (Section 4.5)
